# 路线质量基线（第 1 轮）

测量时间：2026-11-17
图文件：`var/offline/graph.bin`（上海全域，780,000 节点 / 1,505,934 有向边 / 48 MB）

## 这一轮改了什么

`motu-routing` 的成本模型从「距离 / 速度」换成：

```
edge cost = duration_s × class_weight(highway) + turn_penalty(angle)
```

- `profile.rs`：道路等级权重 + 转向惩罚，默认值 `trunk 3.6 / primary 2.4 / secondary 1.5 / tertiary 1.1 / residential 1.0`
- `route.rs`：A* 从「节点状态」改为「有向边状态」，因为经过路口的花费取决于你是怎么进来的
- `metrics.rs`：路线质量指标（干道占比、支路占比、转弯数、信号灯密度）

`--plain` 复现改造前的行为（所有权重 1.0、无转向惩罚），用于对照。

| 指标 | 目标 | 实测（5 条 OD 中位数） | 结论 |

代价：时长普遍上升 30–40%（徐家汇 23→32 min），因为支路限速低、路口多。这是刻意的取舍——目标里“宁可绕一点也要车少”，时长不在验收指标内。

## 两个已知例外

1. **跨江路线无法避开 secondary**：人民广场→陆家嘴只能走复兴东路隧道（OSM 标为 `secondary`），所以干道 20%、支路 0%。指标必须按基线集的中位数判定，单条跨江路线不能套用支路 ≥ 60%。
2. **信号灯指标当前不可得**：Overpass 抽取用的是 `out skel`，节点没有标签，`highway=traffic_signals` 根本没进图。`RouteMetrics::signals_per_km` 因此返回 `None` 而不是 `0.0`——报 0 会让验收假装通过，这正是目标里禁止的“伪造通过”。

## 第 2 轮：信号灯进入成本模型

图中原本**没有任何信号灯数据**：Overpass 抽取用的是 `out skel`，节点不带标签，
`highway=traffic_signals` 根本没进来。这一轮做了三件事：

1. 图格式升到 **v2**：每个节点追加 1 字节信号灯标记；v1 仍可加载，`signals` 为空
2. 抽取语句改成 `out body;>;out body qt;`（第二个 `out` 不再是 `skel`）
3. 成本增加 `signal_penalty = 12 s/个`，并在指标里给出 `signals_per_km`

`signals_per_km` 在图没有信号灯数据时返回 `None` 而不是 `0`——否则“≤3 个/km”
会在根本没测量过的图上直接通过。

### 一个需要决策的发现

**市中心短途的“信号灯密度 ≤ 3 个/km”达不到。**（注：这是第 2 轮只有局部图时的结论；
全量图下 5 条基线 OD 的中位数是 1.6，已达标。此处保留作为边界说明。） 人民广场→外滩即使按最省灯策略也
是 5.8 个/km——市中心路网本身就这么密，1.8 km 内要穿过 10 个路口。

- 郊区/跨区（虹桥、徐家汇一带）：0.9–1.7，达标
- 城郊过渡（中山公园↔豫园 8 km）：3.5，略超
- 市中心短途：5.8，明显超标

四条 OD 的中位数是 3.5，仍高于 3。也就是说**即使改成“中位数 ≤3”，按现有口径
也过不了**：上海中心城区的信号灯密度本身就在这个量级。

这属于**指标口径问题，不是实现问题**：阈值按全城 OD 中位数判定才有意义，若要求
每一条市中心短途都 ≤3，只能造假或删样本——目标里明确禁止。需要使用者决定：
要么改成“基线集 15–20 条的中位数 ≤3”，要么给市中心单独定阈值。

## 第 3 轮：时段先验与连续重算

### 3.1 时段车流先验（L2）

新增 `traffic.rs`：把一天切成若干时间桶，每个桶给每类道路一个成本乘数。

```json
{ "source": "assumption",
  "buckets": [
    { "label": "早高峰", "startHour": 7, "endHour": 10,
      "factors": { "primary": 1.9, "residential": 1.05 } } ] }
```

关键设计：**`source` 字段区分 `measured` 与 `assumption`**，代码里
`PriorSource::is_measured()` 可判定，验收逻辑只接受 `measured`。这样占位先验
不可能冒充实测数据——目标里“不得伪造时段权重”由类型系统兜住，而不是靠自觉。

CLI 已支持：

```bash
motu-graph metrics var/offline/graph-od.bin 31.1951,121.4368 31.3030,121.5150 \
  --hour 8 --prior var/offline/traffic-prior.assumption.json
```

**实测（用 `examples/traffic-prior.json`，source=assumption）**，同一 OD 在 08:00 与
03:00 的路线差异（50 m 容差下差异点占比）：

| OD | h8 距离 | h3 距离 | 差异点占比 | 结论 |
|---|---|---|---|---|
| 徐家汇→五角场 | 18.1 km | 18.0 km | 33% | 不同 |
| 中山公园→豫园 | 8.3 km | 8.2 km | 31% | 不同 |
| 上海南站→虹桥站 | 17.0 km | 17.0 km | 5% | 不同 |
| 人民广场→陆家嘴 | 8.5 km | 8.5 km | 4% | 相同 |
| 静安寺→张江 | 21.2 km | 21.2 km | 4% | 相同 |

**3/5 不同。** 两条没变的原因很清楚：陆家嘴只能过复兴东路隧道，没有替代路线；
静安寺→张江本来就已经 0% 干道，先验没有杠杆可施。

这不是“没做”，而是**先验是假设的，所以差异强度也是假设的**。要让它成为验收
证据，必须先有 `measured` 先验，来源二选一：高德路况 API 定期采样，或积累本人
骑行轨迹。在此之前，验收项“早高峰≠凌晨”只能记为**机制已验证、数据待补**。

### 3.2 连续重算控制器（L3）

新增 `replan.rs`：

```text
偏航 > 50 m                    → 立即重算（3 s 冷却防抖）
更优解 savings ≥ 8%
  且 重合度 ≤ 0.7
  且 距上次切换 ≥ 15 s        → 切换
否则                          → 保持当前路线
```

- `route_overlap(current, candidate, 50 m)`：当前路线有多少比例落在候选折线 50 m 内。
  重合度高说明“同一条路换个折线”，切换对骑手不可见却白烧 CPU。
- `ReplanState::evaluate()` 返回 `Deviation` / `BetterRoute` / `None`，内部维护
  上次切换时间与切换计数。

验收测试 `crates/motu-routing/tests/continuous_replan.rs`：

| 断言 | 结果 |
|---|---|
| 5 次人为偏航全部触发重算 | ✅ 5/5 |
| 每次重算耗时 < 3 s | ✅（网格图上毫秒级） |
| 近乎相同候选导致的路线跳变 ≤ 1 | ✅ 0 次 |
| 30 m 平移判为同一路线（重合度 > 0.9） | ✅ |
| 300 m 平行道路判为不同路线（< 0.1） | ✅ |

## 第 4 轮：车道数与路面（图格式 v3）

`WayInfo` 增加 `lanes` 与 `surface`（`Unknown` / `Paved` / `Unpaved`），图格式升 v3。
成本里：干道每多一条车道（>2）+6%，未铺装 ×1.6；`surface` 缺失保持 `Unknown`
且不加罚。

### 数据覆盖（全部 31,955 条 way）

| 字段 | 有值 | 覆盖率 |
|---|---|---|
| `lanes` | 5,444 | 17% |
| `surface=paved` | 3,712 | 12% |
| `surface=unpaved` | 3 | 0.01% |
| `surface` 缺失 | 28,240 | 88% |

### 对 5 条基线 OD 的影响

**没有变化**：与第 3 轮数字逐项一致（干道 20/5/0/0/2%，支路 9/58/81/58/69%，
灯 1.4/1.6/3.5/1.6/0.9）。原因有两个，都在数据侧：

1. 上海 OSM 中 `surface` 88% 缺失、`unpaved` 只有 3 条，几乎没有“碎石路”可避开
2. `lanes` 只覆盖 17%，且干道权重本来已经很高（primary ×2.4），车道因子只是锦上添花

机制本身由测试锁定（`tests/route_quality.rs`：未铺装短路 + 八车道干道 vs 稍长的
铺装小路，中性剖面走碎石路、摩托剖面走铺装路）。

**结论**：这两项是“补齐目标要求的字段”，不是“提升路线质量的手段”——在现有
OSM 数据下它们对结果没有可观测影响。真要发挥作用，得改用带车道/路面的商业数据
或用 PBF 里的 `width` 推断，那是另一个数据源决策。

### 4.2 禁摩区域改为规划期硬约束

之前禁摩/避让区域只在事后审计（`RoutePlan::crosses`）——路线已经画出来，再告诉你
它穿过了禁区。现在 `RouteContext.avoid` 接收多边形，规划时把落在区域内的**节点**
标为不可进入，A* 直接绕开。

```bash
motu-graph metrics var/offline/graph-od.bin 31.1951,121.4368 31.3030,121.5150 \
  --avoid var/offline/avoid-demo.json     # [[[lat,lon],...]] 每个元素一个多边形
```

真实图实测：在徐家汇→五角场路线的中点（31.24999,121.48493）放一个 ±0.008°
（约 1.8 km）的禁行方块：

| | 距离 | 时长 |
|---|---|---|
| 无禁行面 | 18.03 km | 32 min |
| 加禁行面 | **19.04 km** | **34 min** |

绕行 +5.6%，路线不再进入方块——约束在规划期生效，而不是事后检查。

区域数据来源：`var/motu-web/cache.sqlite` 的 `map_areas`（摩途 `mapShowAreaSec`
缓存，含全国禁区与限行线），只在本机使用、不分发。

## 第 7 轮：基准对比工具与 Android 构建

### 7.1 `motu-parity`：把“相对官方基准 ≤20%”变成可执行检查

```bash
cargo run -p manis-motu-routing --bin motu-parity -- compare \
  --graph var/offline/graph-od.bin --baseline var/offline/baseline-calpath.json \
  --report var/offline/parity-report.md
```

基线文件里每条路线含起终点、官方 distance/duration、以及可选折线。工具会：

- 用本机图重算同一起终点，算**绕行百分比**（超过 +20% 判失败）
- 有折线时算**重合度**（50 m 容差），没有就标注 `—`
- 顺带输出干道/支路占比与灯/km
- 任一条超预算或无法规划 → 退出码非零，数据准备阶段可以据此拦住

基线文件**只存本地、不进仓库**（含厂商算路数据），缺失即跳过，不会悄悄算通过。

**当前状态**：官方 `calPath` 数据还没采集（需要你的摩途账号登录一次）。先用本机规划器

## 第 11 轮：真机偏航重算

Rust 侧的 `ReplanPolicy` 已经通过 `evaluate_after()` 抽成纯函数，JNI 直接把同一套
策略暴露给 Android，避免 Java 里再抄一遍阈值。

新增 JNI：

| 函数 | 作用 |
|---|---|
| `nativeDeviation(points, lat, lon)` | 当前位置到折线的距离（偏航量） |
| `nativeReplanDecision(dev, gain, overlap, msSinceSwitch, hasCandidate)` | 走 `evaluate_after`，返回是否重算与原因 |
| `nativeRouteOverlap(a, b)` | 两条路线重合度（50 m 容差） |
| `nativeRouteFlicker(ref, fresh, lat, lon)` | 只对比「参考路线从最近点往后的那段」，避免把已骑过的部分算成抖动 |

`BaseMapActivity` 里加了一个「模拟 5 次偏航」检查（规划完成后自动跑一次）：
每次从当前路线中段沿垂直方向推开 120 m，量出实际偏航距离，交给决策函数，再重算并计时。

真机结果（Honor，2026-11-17，graph-od.bin，人民广场→陆家嘴）：

```text
重算 5/5 次，最慢 91 ms，越界切换 0 次（预算 3000 ms / 允许 1 次）
#1 偏航 120 m → deviation，重算 91 ms，重合度 0.85
#2 偏航  73 m → deviation，重算 91 ms，重合度 0.77
#3 偏航  61 m → deviation，重算 74 ms，重合度 0.97
#4 偏航 120 m → deviation，重算 68 ms，重合度 0.51
#5 偏航 117 m → deviation，重算 66 ms，重合度 0.68
```

截图：[`images/android-replan.png`](images/android-replan.png)

**这个指标的定义要说清楚**：跳变指的是「不该切换却切换了」（偏航没到 50 m 或候选不够好），
而不是「新路线和旧路线长得不一样」——真偏航之后路线本来就该变。#4 的重合度 0.51 就是
一次合理的改道，不算抖动。

**这套检查没覆盖的**：候选路线触发的切换（省 8% 且重合度 ≤0.7 且距上次切换 ≥15 s）
在真机上没有被触发过，那条路径目前只有 Rust 单测覆盖；也没有用真实 GPS 轨迹跑过。
